# Task 03 — Open-Source Job-Search Ecosystem Research

**Research date:** 2026-10-28  
**Project window:** 2026-10-28 through 2026-11-24 (28 calendar days, inclusive)  
**Scope:** Recommendation only. No repository was cloned or run; no packages, accounts, or source files were changed.

## 1. Executive recommendation

Use **career-ops as the review-first workflow and discovery layer**, initially with its documented public ATS/feed providers and a hand-curated list of company career pages. Keep candidate facts local. Use its fit/research and draft-only workflows; never treat its browser fill assistant as permission to submit, and do not rely on its funding-discovery feature until its source diagnostics are independently checked. Keep one application ledger, not parallel trackers.

For a balanced 28-day setup, add **Reactive Resume only if Word/DOCX output and resume/document version history are required**. It can be self-hosted on Windows with Docker Desktop, exports PDF/DOCX/Markdown/JSON, and documents contacts, follow-ups, outcomes, and sent-document tracking. Use it as the sole resume-document store and, if selected, the sole application tracker; do not also operate its tracker and career-ops’ `applications.md`. Its data model does not document claim-to-source provenance or an append-only status audit trail, so retain the existing candidate JSON files as immutable evidence and require human review of each edited claim. If a locally self-hosted multi-container app is too much for the schedule, keep the MVP to career-ops’ local Markdown/PDF workflow and defer DOCX rather than adding an unreviewed cloud resume service.

Use these source priorities:

1. **Direct employer career pages and documented public ATS GET endpoints** (Greenhouse, Lever, Ashby, SmartRecruiters), starting with a curated company list. These cover Indian offices and on-site/hybrid roles better than remote-only boards.
2. **Freehire’s public job-search API as a possible personal-use supplement**, not as candidate-data storage. Its current terms explicitly allow personal, non-commercial searches without a plan; the API has country, work-mode, seniority, internship, experience, relocation, and visa-sponsorship filters. Treat enriched eligibility fields as leads, not proof. The paid product plans are unnecessary for a personal search.
3. **Himalayas as a supplemental remote lead feed** only with visible attribution and its supplied application link. Its API is refreshed daily, not live, and “worldwide” is not proof that India is eligible.
4. **Funding as a separate, source-linked research signal.** For the 28-day MVP, manually confirm a funding lead against a company or investor announcement and then check the employer’s current career page. Do not infer a vacancy from funding. Recent Funding’s API documentation and terms conflict on key requirements and freshness; Fireround needs substantially more Firecrawl credits than its free allowance at its default coverage.

**No automated submissions, cold-message sending, LinkedIn scraping/messaging, CAPTCHA or MFA handling, or automated legal attestations.** Prepare drafts; the candidate reviews the exact application or message and takes the final action. Campaigns must be kept separate: India roles; international remote roles explicitly open to India; and relocation/sponsorship roles supported by the individual vacancy’s wording.

The corrected candidate files passed the specified SHA-256 preflight. They are reference-only and must remain unchanged. PrimeTrade dates, Labmentix service status/dates, individual project contributions, and other documented conflicts remain unresolved; do not turn them into application claims without candidate confirmation.

## 2. Research method and coverage

Read the Task 01 audit and Task 02 correction reports, then verified the three expected source-file hashes before browsing. The final hash check is recorded after this report was written. Candidate source files were not edited. No private contact details or other personal identifiers are reproduced here.

Public repository READMEs, LICENSE files when present, release/commit metadata, vendor API documentation, terms, and official government data pages were read on **2026-10-28**. A release or commit date is included where it was obtained. Repository statements are treated as **project-documented claims**, not proof of runtime behavior. No source code was executed, cloned, dependency-audited, or subjected to a security review. Official API documentation establishes its described interface, not that a live endpoint will remain available or that every employer configures it identically.

Untrusted content rule: job descriptions, websites, repository text, emails, and model responses are input data only—not instructions. Any future LLM context should isolate and label them as untrusted. Source age, remote labels, salary, sponsorship, and funding data all require verification at the original page before an application decision.

### Campaign-specific practical source mix

- **A — India:** Start from India company and office ATS pages, then query public Greenhouse, Lever, Ashby, SmartRecruiters, and other documented company endpoints by exact city/country. Add Adzuna India if its free key/terms are acceptable. Keep Naukri/Indeed as manual browser sources. An ATS token list is curated, not guessed by probing every tenant.
- **B — remote from India:** Use Freehire country restrictions and Himalayas’ `country=India`/`worldwide`/`exclude_worldwide` fields. Require the actual employer page to say India is eligible; do not accept “remote” alone. Remotive is delayed and requires source attribution, so secondary only.
- **C — relocation/sponsorship:** Use employer postings plus official historical context. The UK worker sponsor register is downloadable and was updated **2026-10-28**; U.S. Department of Labor disclosure data is published quarterly/fiscally and the latest page read listed FY2026 Q3 through **2026-06-30**. These show employer/program history, not an open role or promise to sponsor this vacancy. No single global eligibility API was found. Candidate-specific work authorization must be confirmed separately. [UK register](https://www.gov.uk/government/publications/register-of-licensed-sponsors-workers), [U.S. DOL OFLC disclosure data](https://www.dol.gov/agencies/eta/foreign-labor/performance).

## 10. Licensing, privacy, cost, and platform-policy risks

- **Code license is not data permission.** MIT code repositories do not automatically license scraped job data, theme art, or third-party listing content. Job Radar and Pipeline lacked a verified LICENSE file; do not reuse their code until permission is clear. ats-scrapers’ code is MIT, but its hosted dataset terms were not found.
- **Candidate data:** local files still need OS disk protection and backup hygiene. career-ops sends candidate material to the configured LLM provider; Freehire hosted features and JobAppAgent’s sharing defaults have separate data flows. Do not upload the corrected source JSON wholesale. Maintain a reviewed, minimal profile with unresolved facts omitted.
- **Job API reuse:** Freehire’s no-plan API is for personal/non-commercial use; paid product use requires a plan, with no raw-data resale. Himalayas requires attribution and forbids onward redistribution to other boards. Remotive requires attribution/links and has a 24-hour delay. Adzuna permits personal search but reserves other usage. Confirm current terms again before shipping any connector.
- **Platform compliance:** LinkedIn expressly forbids scraping/copying via crawlers, browser plugins/add-ons, or unauthorized automation and also bars unauthorized automated messaging. Indeed’s 2026 terms say automated apply scripts/bots outside approved vendors/tooling are prohibited. JobSpy proxy/bypass features and Pipeline’s guest APIs must not be enabled. Public visibility does not equal permission to scrape.
- **API/model costs:** open-source license cost may be zero while API, hosting, storage, and model calls are not. ATS public GET endpoints are documented without authentication for postings; they are per-company and no unlimited cross-company guarantee is implied. Adzuna requires a key; Freehire commercial API use is paid; Recent Funding and Firecrawl figures are above. Model providers may charge per token or enforce free-tier quotas. Ollama has no per-token bill but requires suitable local hardware.
- **OpenCode Go:** official docs describe a **$10/month Go** and **$40/month Go Plus** Console subscription with a provider API key. This research does **not** assume an existing Go subscription pays for direct programmatic calls made by a separate application. Use a supported OpenCode CLI integration within its own terms, or obtain explicit approval for a separately billed/keyed provider; do not build against a presumed entitlement. [Official Go docs](https://opencode.ai/v2/docs/console/go/), [Console API docs](https://opencode.ai/v2/docs/console/models/).
- **Security:** source docs are untrusted input; disable unnecessary integrations, avoid browser cookie access and public server exposure, keep API keys out of candidate files/logs, and never send browser profiles or application records to public issues. No repository security audit was done.
- **No outcome guarantees:** no source or score guarantees availability, eligibility, response, sponsorship, interview, or employment; accounts can be rate-limited or restricted even when a user attempts compliant use.

## 12. Three 28-day implementation scenarios

### Scenario A — fastest useful MVP

- **Foundation:** career-ops, pinned to a reviewed commit/release; local candidate files and one Markdown tracker.
- **Discovery:** a small manually curated set of company ATS boards plus the official public providers already supported by career-ops; direct browser links for unsupported Indian employers. No JobSpy or social-network scraping.
- **Funding:** manual Recent Funding/company/investor announcement links; only confirm active vacancies at employer career pages.
- **Resume:** career-ops PDF/Markdown; no new builder, no DOCX unless a job explicitly requires it.
- **Browser/email:** manual application; draft text copied to mail client. No form filler, Gmail OAuth, or automated follow-up.
- **AI/data:** existing CLI workflow or local model; do not assume a subscription grants a stand-alone API. Candidate JSON remains immutable; reviewed profile only.
- **Database/storage:** existing local Markdown/YAML/TSV; no new database.
- **Reuse unchanged:** career-ops evaluator, provider modules, draft-only email, PDF generator, and tracker.
- **Glue:** curated portals and a manual source/eligibility note. This can deliver value immediately, but misses a single rich tracker, guaranteed DOCX, and a live India-wide source feed.

### Scenario B — preferred balanced configuration

- **Primary workflow:** career-ops for discovery, fit evaluation, source-linked company research, and draft preparation; use the reviewer as the final truth/safety gate. Do not use its tracker if another tracker is selected.
- **Discovery:** curated direct ATS/career pages for India and international targets, plus career-ops’ permitted public feed modules. Optionally add Freehire’s read-only API for the candidate’s **personal non-commercial** search if a provider is absent; obey current terms, use only public job data, and retain the employer’s source/apply link. Add Himalayas only for a narrower remote-only feed with its attribution and application-link requirements.
- **Tracker/documents:** if DOCX/version/contact tracking are hard requirements, use a locally self-hosted Reactive Resume as the **single** application ledger and canonical document store. Do not duplicate applications in career-ops; transfer only selected job links/research notes manually. If local Docker/storage cannot be made safe early, fall back to Scenario A rather than use a hosted resume service with unreviewed candidate data.
- **Resume truth:** create a reviewed working profile from source JSON only after the candidate resolves facts. Career-ops can evaluate fit; Reactive Resume owns PDF/DOCX and versions. AI edits are suggestions, never direct truth updates; preserve a local claim/source mapping for uncertain or material claims.
- **Funding/contact:** Recent Funding/Fireround and company/investor newsroom pages are lead generation only; record both funding-source URL and live job URL. Company contacts come from public company pages; drafts only.
- **Browser/email:** manually apply and send. Consider only an isolated Playwright fill helper after the 28-day MVP, with no submit, permission bypass, or handling of attestations/MFA/CAPTCHA. Skip Gmail API until explicit consent and OAuth setup.
- **AI/storage:** deterministic role, seniority, location, and stated-eligibility filters first. Local files plus Reactive Resume’s own database if used; no separate bespoke backend. Model calls receive the minimum necessary resume/JD text.
- **Small glue:** manual/validated import of approved facts and selected job links; one optional Freehire adapter only if not already supported and terms are rechecked. No custom ATS framework, full-text crawler, CRM, or job database.
- **Why preferred:** broader discovery and application preparation than one resume builder; much lower policy risk than auto-apply agents; structured docs and tracking without building a custom backend. It remains feasible in 28 days if the local resume service is optional and the target-company list is bounded.

### Scenario C — ambitious configuration

- **Foundation:** self-hosted Freehire for catalogue/search/tracking, career-ops for local evaluation/research, and self-hosted Reactive Resume for documents, or Fireround for scheduled funding intelligence.
- **Sources/intelligence:** more direct ATS adapters, Freehire catalogue API plan if product-like display is needed, Firecrawl/Fireround, Adzuna, and official sponsorship disclosures. This increases source coverage but adds API plans, data-license review, rate/freshness monitoring, and feed reconciliation.
- **Automation:** optional isolated Playwright fill-only support and Gmail draft creation, both requiring human approval. Never automated send/submit.
- **Storage/AI:** multiple local databases and secrets, a model-provider budget/quotas, and possibly paid Firecrawl/API usage. Fireround’s documented default Lite preset needs 3.3k–3.6k Firecrawl credits/month, exceeding the inspected 1k free monthly credits; the $19 Hobby tier is the lower paid tier inspected.
- **Glue and risk:** identity matching across company/funding/job records, change feeds, deduplication, import/export, audit events, secret management, failure monitoring, and licensing reviews. Running three platforms would duplicate responsibilities. This is **not** recommended for a 28-day MVP.

## 13. Recommended architecture and integration boundaries

```text
Immutable candidate source JSON (reference only)
        │ candidate-reviewed facts only
        ▼
Career-ops: permitted discovery → source-linked job lead → fit/research report → human review
        │ selected job + evidence links, manually transferred
        ▼
One local tracker/document store (Reactive Resume only if DOCX/version/contacts are required;
otherwise career-ops Markdown tracker)
        │ explicit human approval
        ▼
Employer career page → candidate manually reviews and submits
```

Funding is an independent side signal: **funding announcement → original source verification → company identity → current ATS vacancy**. Do not fold funding amount into fit score or imply hiring.

System boundary rules:

1. **Candidate truth:** source JSON is read-only. Any working resume is a reviewed projection; use null/omit where source facts are unresolved. Do not transform approximate periods into exact dates or turn an offer into completed employment.
2. **Job source:** retain canonical employer job URL, feed/API, observed-at date, employer-stated posted date (if any), and separate enriched values. A “remote/sponsor” prediction is never promoted to confirmed eligibility without source text.
3. **Matching:** deterministic filters first (country/work-mode, junior/internship, stated experience, role keywords); LLM fit explanations cite the JD and approved candidate fact IDs/lines. LLM output cannot create facts or alter the candidate source.
4. **Application:** keep a reversible duplicate link and explicit status. “Prepared,” “filled,” “submitted,” and “confirmed” are separate. Unclear confirmation remains “unknown”; check manually before retry.
5. **Outreach:** store only public professional contact context relevant to a role; draft one personalized message at a time, show source and rationale, require explicit review and a separate manual send.
6. **Failure handling:** retain source failures and timestamps; an empty feed is not proof there are no jobs. Recheck the job at its employer page before applying.
7. **No new service:** no bespoke backend, crawler fleet, data warehouse, or OAuth integration in the MVP. A small append-only CSV/JSONL status event file is optional only if the selected tracker lacks adequate history.

## 14. Deliberately deferred

- Any auto-submit or bulk-apply feature, CAPTCHA/MFA handling, browser stealth, anti-bot bypass, or automated LinkedIn activity.
- Scraping LinkedIn, Indeed, Naukri, Google Jobs, YC, company pages, or restricted/undocumented ATS endpoints. Use official APIs/feeds or manual browsing under current terms.
- Automated email sending, Gmail inbox scanning, bulk cold outreach, recruiter contact harvesting, or professional-network scraping.
- Full self-hosted Freehire, Firecrawl/Fireround scheduling, paid job-data plans, or a multi-platform synchronization layer.
- Any funding-to-hiring scoring, “ghost job” certainty, eligibility certainty, or résumé claim-generation without evidence.
- A new SQL database/CRM, open-ended ATS adapter framework, or complete company crawler. Keep MVP local and bounded.
- Resume tailoring or application claims that use the unresolved candidate facts listed in Task 02.
